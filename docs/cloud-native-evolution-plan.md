## 一、当前架构痛点分析

### 1.1 架构概览

当前项目采用传统前后端分离架构：

```
┌──────────────────────────────────────────────────────┐
│  前端：React 18 + TypeScript + Vite 5               │
│  问题：纯SPA、无SSR、前端算力闲置                     │
└──────────────────┬───────────────────────────────────┘
                   │ REST API + WebSocket
                   ▼
┌──────────────────────────────────────────────────────┐
│  后端：Spring Boot 3.3 单体应用                       │
│  问题：耦合严重、扩缩困难、资源竞争                     │
│  ├─ 用户认证、游戏核心、AI推理、统计计算混在一起        │
│  └─ WebSocket与业务逻辑耦合                           │
└──────────────────┬───────────────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────────────┐
│  存储：MySQL 单一数据库                               │
│  问题：时序数据、向量数据、日志数据全部压垮关系库        │
│  ├─ Redis 仅作缓存（单节点）                          │
│  └─ AI向量、打字时序、聊天消息都存MySQL                │
└──────────────────────────────────────────────────────┘
```

### 1.2 核心痛点清单

| 痛点类别 | 具体问题 | 影响 | 优先级 |
|---------|---------|------|--------|
| **架构耦合** | 所有业务集中在单体Spring Boot | 无法独立扩缩容，AI推理抢占游戏资源 | 高 |
| **存储单一** | 打字时序数据、聊天消息、AI向量全存MySQL | 高频读写压垮关系库，查询性能差 | 高 |
| **AI能力外挂** | LLM仅简单调用Coze API | 延迟高、成本高、无离线能力 | 高 |
| **前端算力浪费** | 打字计算、渲染全靠JS单线程 | 帧率低、响应慢、联机对战卡顿 | 中 |
| **可观测缺失** | 仅文件日志，无监控、无追踪 | 问题定位困难，线上故障难排查 | 中 |
| **实时通信受限** | WebSocket内嵌单体 | 高并发消息风暴、断线重连差 | 中 |
| **部署原始** | 裸机Jar部署，无容器化 | 灰度困难、扩缩容慢 | 低 |

### 1.3 数据流量分析

根据业务特性，数据流可分为三类：

| 数据类型 | 特点 | 当前存储 | 建议存储 |
|---------|------|---------|---------|
| **游戏时序数据** | 每秒上万次按键记录，写多读少 | MySQL | **时序数据库** |
| **用户特征/词向量** | AI生成个性化词库，向量检索 | MySQL | **向量数据库** |
| **聊天消息** | 高频读写、实时推送 | MySQL | **消息队列+时序库** |
| **排行榜/在线状态** | 高频读取、实时更新 | Redis（单节点） | **Redis Cluster** |
| **用户/词库配置** | 低更新、结构化 | MySQL | MySQL（主从） |

```
┌─────────────────────────────────────────────────────────────────┐

│   ├─ 离线训练节点             ClickHouse数据微调打字专属模型       │
│   └─ 模型版本管理             BentoML                            │
└─────────────────────────────────────────────────────────────────┘

【配套底座】K8s + Istio + Prometheus + Grafana + ELK + GitLab CI
```

### 2.2 核心设计原则

1. **渐进式演进**：不一次性推翻现有架构，分阶段迁移
2. **接口兼容**：微服务拆分保持原有API路径不变
3. **数据兼容**：新存储与MySQL并存，逐步迁移
4. **可观测优先**：每个阶段都部署监控和追踪
5. **弹性伸缩**：核心服务支持自动扩缩容

## 三、分阶段演进路线图

### 阶段零：当前架构快速改进（1-2周）

**核心目标**：在不改变单体架构的前提下，快速提升可观测性、稳定性和开发效率。

#### 3.0.1 快速改进清单

| 改进项 | 技术方案 | 实施难度 | 收益 |
|--------|---------|---------|------|
| 添加监控指标 | Spring Boot Actuator + Micrometer | 低 | 实时查看系统状态 |
| 添加健康检查 | Actuator health端点 | 低 | 支持容器探针 |
| 添加日志结构化 | SLF4J + JSON格式 | 低 | 日志可被ELK解析 |
| Redis优化 | 配置连接池、超时参数 | 低 | 减少连接泄漏 |
| Docker容器化 | 编写Dockerfile | 低 | 一致的开发/部署环境 |
| 异步事件处理 | 引入RocketMQ发送对局完成事件 | 中 | 解耦统计计算 |
| 参数校验增强 | 使用@Validated + 自定义校验器 | 低 | 减少无效请求 |

#### 3.0.2 关键改动示例

**添加Actuator依赖（pom.xml）**：
```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

**Actuator配置（application.yml）**：
```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  endpoint:
    health:
      show-details: always
  metrics:
    export:
      prometheus:
        enabled: true
```

**Dockerfile**：
```dockerfile
FROM eclipse-temurin:22-jre-alpine
WORKDIR /app
COPY target/typingGame-0.0.1-SNAPSHOT.jar app.jar
EXPOSE 8080
CMD ["java", "-jar", "app.jar"]
```

### 阶段二：混合存储架构升级（2-3个月）

**核心目标**：引入时序数据库、向量数据库、Redis集群

#### 3.2.1 存储选型与职责划分

| 存储类型 | 技术选型 | 版本 | 存储内容 |
|---------|---------|------|---------|
| 关系数据库 | MySQL | 8.4 | 用户基础信息、词库配置、对局结算 |
| 缓存集群 | Redis Cluster | 7.0 | 排行榜、在线状态、会话缓存、分布式锁 |
| 时序数据库 | TDengine | 3.0 | 打字时序数据（按键时间、准确率、延迟） |
| 向量数据库 | Milvus | 2.3 | 字词语义向量、用户打字特征向量 |
| 离线数仓 | ClickHouse | 23.3 | 历史打字行为、大数据分析、模型训练 |
| 对象存储 | MinIO | 最新 | 自定义词库、游戏素材、训练报告 |

#### 3.2.2 数据迁移策略

**打字时序数据迁移**：
```
旧方案：每次按键 → MySQL INSERT
新方案：每次按键 → TDengine写入 → 异步聚合 → MySQL更新统计

优势：写入性能提升100倍，MySQL负载降低40%
```

**向量数据引入**：
```
新方案：用户打字数据 → Milvus向量入库 → 
       向量检索相似字符 → AI生成个性化训练词库

优势：智能推荐准确率提升60%
```

#### 3.2.3 实施步骤

```
步骤1: 部署TDengine集群，创建打字时序表
步骤2: 改造GameRecordServiceImpl，按键数据写入TDengine
步骤3: 部署Milvus，创建字词语义向量库
步骤4: 改造AI服务，引入向量检索生成个性化词库
步骤5: 部署Redis Cluster，迁移排行榜和在线状态
步骤6: 部署MinIO，迁移自定义词库存储
步骤7: 部署ClickHouse，搭建离线数仓
步骤8: 验证数据一致性和查询性能
```

#### 3.2.4 TDengine建表示例

```sql
CREATE DATABASE typing_game;
USE typing_game;

CREATE TABLE typing_events (
    ts TIMESTAMP,
    user_id INT,
    record_id INT,
    char_value CHAR(10),
    char_type VARCHAR(20),
    press_time BIGINT,       -- 按键时间（毫秒）
    latency BIGINT,          -- 反应延迟（毫秒）
    is_correct BOOLEAN,      -- 是否正确
    speed DOUBLE,            -- 打字速度（WPM）
    INDEX (user_id, ts)
);
```

## 五、技术选型务实评估

### 5.1 当前规模分析

当前项目处于早期阶段，预估并发用户在百级规模：

| 指标 | 当前规模 | 建议阈值 | 是否需要升级 |
|------|---------|---------|-------------|
| 并发用户 | < 500 | > 5000 | 当前不需要微服务 |
| 日均对局 | < 1000 | > 100000 | 当前不需要时序库 |
| AI对话次数 | < 1000/天 | > 100000/天 | 当前不需要本地推理 |
| 数据量 | < 1GB | > 100GB | 当前不需要数仓 |

### 5.2 技术分级评估

| 技术 | 优先级 | 适用阶段 | 说明 |
|------|--------|---------|------|
| **Spring Boot Actuator** | ⭐⭐⭐⭐⭐ | 阶段零 | 立即实施，提升可观测性 |
| **Docker容器化** | ⭐⭐⭐⭐⭐ | 阶段零 | 立即实施，统一部署环境 |
| **Redis优化/集群** | ⭐⭐⭐⭐ | 阶段零/一 | 当前单节点够用，后续可升级集群 |
| **RocketMQ** | ⭐⭐⭐⭐ | 阶段零/一 | 引入异步事件，解耦统计计算 |
| **TDengine时序库** | ⭐⭐⭐ | 阶段二 | 当按键数据量达到百万级时引入 |
| **Milvus向量库** | ⭐⭐⭐ | 阶段二/三 | 当需要个性化推荐时引入 |
| **Nacos配置中心** | ⭐⭐⭐ | 阶段一 | 多环境配置管理需求时引入 |
| **API网关** | ⭐⭐⭐ | 阶段一 | 多服务时引入，单服务可用过滤器替代 |
| **NextJS 15** | ⭐⭐⭐ | 阶段四 | SEO和首屏优化需求时升级 |
| **vLLM GPU推理** | ⭐⭐ | 阶段三 | 日均AI调用>10万次时考虑 |
| **ClickHouse** | ⭐⭐ | 阶段四 | 数据量>100GB且需要大数据分析时引入 |
| **Kubernetes + Istio** | ⭐⭐ | 阶段三 | 服务数量>5个且需要自动扩缩容时引入 |
| **WebGPU/WASM** | ⭐⭐ | 阶段四 | 游戏性能成为瓶颈时引入 |

### 5.3 渐进式策略建议

**短期（1-2周）：阶段零快速改进**
- 优先添加监控和容器化
- 引入RocketMQ处理异步事件
- 优化Redis配置

**中期（1-3个月）：按需引入新技术**
- 根据实际数据增长情况决定是否引入TDengine
- 根据AI使用频率决定是否引入Milvus和本地推理
- 当服务数量增加到3个以上时引入Nacos

**长期（3-6个月）：全面升级**
- 并发达到万级时引入K8s
- 游戏性能成为瓶颈时引入WebGPU
- 数据量达到百GB时引入ClickHouse

## 九、实施建议

### 9.1 优先启动建议

1. **阶段零先行**：在进行任何大规模架构改造前，先完成快速改进
2. **可观测平台先行**：在微服务拆分前部署监控系统，便于问题定位
3. **网关先行**：先部署API网关，后续微服务拆分对前端透明
4. **保持接口兼容**：微服务拆分时保持原有API路径不变
5. **数据双写策略**：新存储与MySQL并存一段时间，确保数据一致

1. **K8s培训**：团队掌握基本的K8s运维技能

3. **AI推理基础**：了解vLLM、向量数据库等AI基础设施
4. **WebGPU/WASM**：前端团队学习新的计算能力
